# The LLM Wiki pattern

## Definition

A knowledge base where an LLM **incrementally builds and maintains a persistent, interlinked
collection of markdown files** that sits between you and the raw sources. When a new source
arrives, the model does not merely index it for later retrieval — it reads it, extracts the
key information, and integrates it into the existing wiki: updating entity pages, revising
topic summaries, noting where new data contradicts old claims, and strengthening or
challenging the evolving synthesis. ^[raw/articles/karpathy-llm-wiki-gist.md]

The distinguishing property is that **the wiki is a persistent, compounding artifact**.
Cross-references are already there. Contradictions have already been flagged. The synthesis
already reflects everything read. It gets richer with every source added and every question
asked. Contrast [[llm-wiki-vs-rag]].

## Division of labor

> "You never (or rarely) write the wiki yourself — the LLM writes and maintains all of it.
> You're in charge of sourcing, exploration, and asking the right questions."
> ^[raw/articles/karpathy-llm-wiki-gist.md]

The model does the summarizing, cross-referencing, filing, and bookkeeping "that makes a
knowledge base actually useful over time". The human curates sources and directs analysis.
^[raw/articles/hermes-agent-llm-wiki-skill.md]

This is the load-bearing assumption of the whole pattern — and the reason
[[human-in-the-loop-review-gate]] exists. If the model owns the compiled layer entirely,
then the compiled layer is only as trustworthy as the model's judgment about what is true.

## Three operations

**Ingest.** Drop a source into the raw collection, tell the model to process it. It reads
the source, discusses takeaways, writes a summary page, updates the index, updates relevant
entity and concept pages across the wiki, and appends a log entry. A single source might
touch 10–15 pages. Karpathy prefers ingesting one at a time while staying involved; batch
ingest with less supervision is also viable, and the chosen workflow should be documented in
the schema. ^[raw/articles/karpathy-llm-wiki-gist.md]

**Query.** Ask questions against the wiki. The model searches for relevant pages, reads
them, synthesizes an answer with citations. Answers can be a markdown page, comparison
table, slide deck, chart, or canvas. The key insight: **good answers get filed back into the
wiki as new pages**, so explorations compound like ingested sources instead of disappearing
into chat history. ^[raw/articles/karpathy-llm-wiki-gist.md]

**Lint.** Periodically health-check: contradictions between pages, stale claims superseded
by newer sources, orphan pages with no inbound links, important concepts mentioned but
lacking a page, missing cross-references, and data gaps a web search could fill. The model
is also good at suggesting new questions to investigate.
^[raw/articles/karpathy-llm-wiki-gist.md]

## Navigation files

`index.md` is **content-oriented** — a catalog of every page with a link and one-line
summary, organized by category, updated on every ingest, and read first when answering a
query. It "works surprisingly well at moderate scale (~100 sources, ~hundreds of pages) and
avoids the need for embedding-based RAG infrastructure." ^[raw/articles/karpathy-llm-wiki-gist.md]

`log.md` is **chronological** — append-only, with a consistent entry prefix
(`## [2026-04-02] ingest | Article Title`) so the log stays parseable with plain unix tools:
`grep "^## \[" log.md | tail -5`. ^[raw/articles/karpathy-llm-wiki-gist.md]

Both are implemented here, with `index.md` machine-generated by `tools/wiki_tool.py
reindex` and `log.md` appended by every tool action. See
[[three-layer-wiki-architecture]].

## Application domains named by the source

Personal (goals, health, psychology — filing journal entries and podcast notes) · research
(weeks or months on a topic, building an evolving thesis) · reading a book (chapter by
chapter, building character/theme/plot pages, like a personal Tolkien Gateway) ·
business/team (fed by Slack threads, meeting transcripts, project docs, customer calls,
"possibly with humans in the loop reviewing updates") · competitive analysis, due
diligence, trip planning, course notes, hobby deep-dives.
^[raw/articles/karpathy-llm-wiki-gist.md]

## Current state

The pattern is now an ecosystem, not a gist: an `awesome-llm-wiki` catalog of foundations,
frameworks, tutorials, tools, MCP servers, reference vaults, papers, courses, videos and
podcasts; architectural extensions (v2 memory lifecycles and confidence decay, v3
state-space belief graphs, v3 segmentation into Ingestor/Librarian/Linter roles with dual
ingestion modes); and a built-in shipping implementation in [[hermes-agent]].
^[raw/articles/awesome-llm-wiki-readme.md] See [[open-source-agent-skills]].

## Open questions and debates

- **Scale.** Index-first navigation is claimed sufficient to "~hundreds of pages". Beyond
  that, hybrid retrieval reappears in several implementations. No captured source measures
  the actual ceiling.
- **Trust.** Who decides a synthesis is true? The pattern's answer is "the human curates
  sources"; [[anti-slopification]] argues that is insufficient once the compiled layer
  becomes the thing the agent reads.
- **Drift.** Segmentation-era writing names "context drift and schema overload" as the
  failure mode of large wikis, proposing specialized roles and explicit schema triggers.
  ^[raw/articles/awesome-llm-wiki-readme.md]
- **Memory vs wiki.** Whether an agent's memory system should subsume the wiki. See
  [[agentic-memory-vs-compiled-wiki]].
